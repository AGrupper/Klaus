<objective>
Move every occasion compose onto the full-CPU dispatch path and add the morning's push
trigger.

D-32 names a real defect: `/trigger/nightly` composes in a Starlette `BackgroundTask`,
which CLAUDE.md's own invariant forbids — Cloud Run throttles CPU once no request is in
flight, and that is exactly the class of bug that produced the 2026-06-12 18-minute reply.
It survives today only because the nightly compose is a single LLM call. Under the agentic
Layer 2 this phase ships, it very likely will not. `/trigger/morning` would have inherited
the same shape, so both trigger routes get the proven enqueue-then-202 treatment, and the
`/cron/*` occasions move to the same path for consistency and request-timeout headroom
(honest caveat from D-32: those are not broken today, because holding the request open
keeps CPU allocated — the trigger routes are the actual defect).

D-13 gives the morning its own bearer secret: a leaked credential must not unlock every
proactive surface. D-31 ships the route dark — it deploys and does nothing until Amit's
Sleep-Focus-off Shortcut starts hitting it, and `morning-briefing-tick` stays running until
then, so there is no silent-morning gap.

Purpose: OCC-02's trigger surface and OCC-06's dispatch correctness.
Output: `enqueue_occasion`, `/internal/process-occasion`, `/trigger/morning`, and the
rewired `/trigger/nightly` + `/cron/*` occasion routes.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public internet (iOS Shortcut) → `POST /trigger/morning` | Unauthenticated caller reaching a route that causes Klaus to message Amit and write to his calendar |
| Cloud Tasks → `POST /internal/process-occasion` | Machine-to-machine call that executes a full agentic turn with write-capable tools |
| Cloud Scheduler → `/cron/*` occasion routes | Existing OIDC boundary, now also an enqueue surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33-01 | Spoofing | `POST /trigger/morning` | mitigate | Dedicated `MORNING_TRIGGER_TOKEN` bearer secret verified with `hmac.compare_digest` (constant-time, never `==`); refuse-all HTTP 500 when the env var is unset so a failed Secret Manager mount cannot fail open; no fallback to `NIGHTLY_TRIGGER_TOKEN` (D-13 least privilege); failed attempts logged with a redacted 4+4 token prefix and the client host |
| T-33-01b | Information Disclosure | trigger-auth failure logging | mitigate | The received token is never logged in full — only `received[:4] + "..." + received[-4:]`, and only when at least 8 characters, exactly as `_verify_trigger_request` already does |
| T-33-04 | Spoofing | `POST /internal/process-occasion` | mitigate | Gated by the existing `_verify_cron_request` OIDC verification against `CLOUD_RUN_URL` as audience and `CLOUD_SCHEDULER_SA_EMAIL` as the expected service account; `enqueue_occasion` reuses the same SA and audience so no new trust relationship is created |
| T-33-32 | Tampering | `occasion` value in the Cloud Tasks body | mitigate | Validated against the literal set `{"nightly", "morning", "weekly_review"}` and rejected with 400 otherwise, so a malformed or hostile body cannot select an arbitrary dispatch target |
| T-33-33 | Denial of Service | CPU-throttled background compose (the D-32 defect) | mitigate | All four occasion routes enqueue and ACK; `_run_nightly_background` is deleted; a grep assertion proves no new `background_tasks.add_task` was introduced |
| T-33-34 | Denial of Service | Cloud Tasks outage silently dropping a trigger | mitigate | `enqueue_occasion` returns `False` rather than raising, and every caller surfaces 503 so the iOS Shortcut and Cloud Scheduler both see a retryable failure instead of a silent success |
| T-33-SC | Tampering | npm/pip/cargo installs | accept | No packages installed in this phase (33-RESEARCH.md § Standard Stack) |
</threat_model>
