<objective>
Give Klaus the ability to account for himself.

OCC-07 in one sentence: "why didn't you message me yesterday?" must get a real answer.
D-26 makes that concrete — four things, one tool, one place: the verdict and triage
reasoning per run; what was sent and when; the actions taken (the D-25 records); and the
skip cause categorised into one of D-02's four. Default two days, callable further for
pattern questions.

This is also the phase's live debugging surface. D-28 makes "ask Klaus" half the rollout
watch strategy, alongside the heartbeat anomalies — so the tool has to work from real
production records, not a bespoke shape.

D-27 constrains the *use*, not the contract: skips never surface unasked. This handler just
returns data; the "never volunteer it" rule lives in `prompts/autonomous.md` (plan 33-03)
and is enforced structurally by plan 33-04 never rendering skip records into a compose
prompt. Undisclosed *actions* are the deliberate exception.

Purpose: OCC-07, plus the observation window's primary human-facing instrument.
Output: `get_recent_decisions(days)` — schema, handler, and the three-touch-point
brain-direct registration.
</objective>

  <action>
    Add `_handle_get_recent_decisions(days: int = 2) -> str` to `core/tools.py`, placed next
    to the other brain-direct read handlers.

    **Input validation first (ASVS V5).** `days = max(1, min(int(days), 30))` before it
    drives anything. Reject nothing — clamp, so an LLM-supplied `1000` or `-5` cannot fan a
    Firestore read out beyond a month. Return the clamped value in the payload's `days` field
    so the brain knows what it actually got. 33-PATTERNS notes no existing handler clamps a
    numeric arg; this is new code, so write it explicitly rather than looking for a precedent
    to copy.

    Build the date list: the last `days` Asia/Jerusalem calendar dates, newest first,
    inclusive of today.

    For each date:
      - `TickLogStore(...).ticks_for_date(date)` → for each entry, read `decision_trail` and
        flatten into a `decisions` row. `kind` is `"occasion"` when the entry's `time` doc id
        starts with `"occasion:"` (the doc-id convention plan 33-04 established), `"tick"`
        otherwise. Pull `should_act` and `reason` out of the trail's `{"layer1": verdict}`
        element; pull `skip_cause`, `sent`, `composed_via` and `topic_key` from the decision
        dict's top-level keys. Missing keys degrade to `None`/`""`/`False` — old tick logs
        written before this phase have none of them and must not crash the read.
      - `OutreachLogStore(...).get_today(date)` → `sent` rows carrying the full `final` text,
        so "what did you actually say" is answerable.
    Then one `ActionLogStore(...).get_recent(days)` call for the `actions` list.

    Every store read is already never-raises by contract; wrap the whole handler in a
    try/except that returns `json.dumps({"error": str(exc)})` rather than propagating, matching
    the surrounding handlers' posture.

    **ISO safety.** Route every dict that reaches `json.dumps` through `_jsonsafe_doc` (import
    it from `memory.firestore_db`) and keep `default=str` on the `json.dumps` call as a second
    line of defence. `captured_at`, `updated_at` and any SERVER_TIMESTAMP round-trip arrive as
    `DatetimeWithNanoseconds`, which breaks `json.dumps` — this exact bug has bitten MealStore
    and TrainingLogStore in this repo.

    **D-27.** No filtering or redaction happens here; the handler returns skip records
    faithfully. The "never surface unasked" rule is a prompt-level and compose-level
    constraint, already handled by plans 33-03 and 33-04. Note that in the docstring so a
    future reader does not add redaction logic here by mistake.
